# 0.2.0rc4 实时链路验证记录（2026-09-28）

本版目标是把原 Gradio 摄像头入口改造成可以测量的连续实时入口，同时保留原有视频处理页面。

## GPU 环境

新建 `.venv-gpu`，没有继承 `.venv` 或系统 site-packages。实测版本：Python 3.10.16、Torch 2.5.1+cu121、TorchVision 0.20.1+cu121、NumPy 1.26.4、OpenCV 4.10.0.84、FastAPI 0.111.1、Uvicorn 0.50.1、websockets 11.0.3。`pip check` 无冲突，CUDA 张量计算通过；设备为 NVIDIA GeForce GTX 1660 Ti，显存 6,442,123,264 bytes。完整清单为 `requirements-lock-windows-py310-cu121.txt`。

## 自动化验证

- CPU `.venv` 中全量工程回归：**666 passed、1 skipped**；覆盖率 **90.35%**，达到项目 70% 门槛。实时服务、协议、启动器、验收脚本和前端控制器针对性测试为 **140 passed**。
- 前端内联 JavaScript 通过 Node 语法检查，页面无 CDN、无外部脚本。
- 服务验证了 JPEG 尺寸/大小边界、同源 Origin、单会话席位、模型包身份、源码身份、帧顺序、重置、断开清理和错误回收。
- 运行时只允许一帧在途；服务端队列和 Uvicorn WebSocket 消息上限均为 1/2 MiB 级别，避免慢设备积压。

## 真实 GPU 服务基准

脚本 `scripts/verify_realtime.py` 使用真实离线 RVM MobileNetV3，在 `127.0.0.1` 启动真实 Uvicorn/WebSocket 服务，合成 1280×720 移动图形逐帧缩放到目标宽度后发送，预热 10 帧，总计 120 帧。空 Torch 缓存和下载入口受到拦截，服务退出后自己的进程已回收。

| 宽度 | 预热后服务处理 p50 | 预热后服务处理 p95 | 预热后往返 p50 | 预热后交付 FPS | 峰值已分配显存 |
|---:|---:|---:|---:|---:|---:|
| 320 | 20.39 ms | 24.74 ms | 22.57 ms | 33.71 | 37.3 MiB |
| 640 | 44.71 ms | 49.97 ms | 48.38 ms | 17.82 | 92.1 MiB |
| 960 | 87.19 ms | 96.72 ms | 93.02 ms | 9.45 | 99.1 MiB |

首帧包含模型首次调用和 CUDA 预热，三个宽度的首帧往返约 2.86–4.40 秒；实时显示应把首帧准备单独说明。服务处理时间范围从 JPEG 解码、服务端缩放、RVM 推理、合成到 JPEG 编码；往返时间还包含本地传输和客户端 JPEG 解码，不含远程网络。最终提交后的复验报告分别保存于 `data/output/v0.2.0rc4/rehearsal-gpu-{320,640,960}-final/rehearsal.json`。

服务在 Windows 下主动结束时报告退出码 1，但 `service_reaped=true`，表示自己的服务已经等待回收；这不表示帧处理失败。三次报告 `passed=true`，模型包内容 SHA256 均为 `dcfca84453ff1c932240ab2aa0bcada6bedc85e93f4b9a60a49555e70a0ea375`。

## 结论与边界

当前 GTX 1660 Ti 6GB 在 320 宽达到约 33.7 FPS 的服务基准，在 640 宽达到约 17.8 FPS；推荐实时答辩默认 640 宽并接受约 15–18 FPS，若优先流畅度选择 320 宽。这个结果不能外推到真人抠像质量、摄像头浏览器端到端帧率、远程 HTTPS/WSS、多人并发或长时间热稳定性。

仍需在目标答辩机上完成实际浏览器摄像头授权、不同浏览器、远程 HTTPS/WSS、真人素材及连续运行温度/显存观察。当前实时服务明确只允许一个活动会话，第二个连接会被拒绝，避免多个会话争抢单卡循环状态。
